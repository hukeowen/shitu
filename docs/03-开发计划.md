# 03 · V1.0 开发计划

## 1. 工期判断

《版本规划》给 V1.0 的估算是「后端 2 + 前端 1 + 测试 1，5–6 周」。原型实际做了 95 屏，而且在文档之外补了不少内容（OCR 合规、题库和引擎配置、工资、打卡、审计）。**按原型全量做，5–6 周做不完。**

| 方案 | 范围 | 工期 |
|---|---|---|
| **推荐：P0 + P1** | 01-功能清单中所有 P0、P1；P2 和打卡放到 V1.5 | **12 周**（10 周开发 + 2 周联调、UAT 和试点） |
| 压缩：只做 P0 | 只做闭环；题库和引擎用种子配置；OCR 只做两次输入比对 | 8 周 |
| 全量 | 包含 P2 和打卡 | 14–15 周 |

另外，**第三方资质和账号的审批周期**（ICP 备案、人力资源服务许可证、短信签名、e签宝合同）通常要 2–4 周，必须在第 1 周就启动，否则 W6 联调电子签时会被卡住。

## 2. 里程碑

| 里程碑 | 时间 | 交付 / 验收 |
|---|---|---|
| M0 启动 | W1 末 | 原型按 05-核验报告和 04-决策记录完成修正；仓库、CI、数据库 v1 跑通；第三方申请已提交 |
| M1 可匹配 | W5 末 | 扫码注册 → 答题 → 出 3 个岗位 → 实名报名 → 驻场收到待办，**走通全链路**（第三方用 Mock） |
| M2 可入职 | W7 末 | 到厂 → 确权 → 电子签（沙箱）→ 在岗；爽约、取消、24h 超时释放全部能跑 |
| M3 可收钱 | W9 末 | 流转与释放、离职、花名册和存量锁定、每日计费、月账单、流转账本 |
| M4 功能完整 | W11 末 | 预支、风控、看板报表、平台中台全部完成；冻结功能 |
| M5 上线 | W13 末 | 回归测试、压测、安全测试通过；1–2 家试点企业上线 |

### Sprint 1 · W2–W3 · 账号、租户、岗位（先有数据，才能匹配）

- 后端：`identity`（短信登录、JWT、图形验证码）、渠道码（生成二维码短链、302 跳转与暂存）、`tenant`（入驻、成员、角色、项目、甲方）、`job`（CRUD、审核、暂停、下架、名额）
- 公司后台：登录、组织与权限 T-502、渠道二维码 T-501、项目管理、岗位管理 T-301~T-303
- 平台中台：登录、公司管理与入驻审核 P-02、岗位审核 P-04、平台账号 P-15、审计日志 P-11
- C 端：启动页和渠道识别 C-101、游客首页和引导弹窗 C-102/103、注册 C-104/105/106

### Sprint 2 · W4–W5 · AI 问薪、实名报名、状态机核心 → **M1**

- C 端：首页 5 种状态 C-201~204、问薪全流程 C-301~306、岗位详情 C-401、告知书 C-403、实名 C-404~406、报名成功 C-407、我的报备 C-501、消息中心 C-507
- 驻场端：工作台 M-01、待面试 M-02（知悉 → 推送面试信息）
- 平台中台：题库配置 P-12（可先做只读 + 发布）
- **验收**：并发 50 人抢最后 1 个名额只有 1 人成功；报名后再进入问薪会被拒绝；24h 到期（测试环境把窗口调成 5 分钟）自动释放，并写入日志和通知；匹配结果可以凭快照复现

### Sprint 3 · W6–W7 · 入职闭环 → **M2**

- 后端：`employment`（确权、电子签适配器和回调、合同、调岗）；面试结果、爽约、后台取消；跟进提醒任务 J-03

- 公司后台：驻场 PC 端 T-101~T-103、人员管理 T-307
- C 端：面试信息 C-408、我的工作 C-505、我的合同 C-503、身份卡 C-502、动态提醒 C-203
- **验收**：签约回调重复推送也只入职一次；签约完成后项目经理和老板都收到推送；爽约、取消、面试未通过三条路径都正确回补名额并释放到公域

### Sprint 4 · W8–W9 · 流转、离职、计费 → **M3**

- 后端：`circulation`（流转池、AI 报告、二次推荐、释放、SLA）、离职流程、花名册导入、存量锁定 J-07、`billing`（J-01 每日计费、J-10 月账单、异议）、公司注销批量解绑

- **验收**：用**计费黄金用例集**（不少于 30 个场景：当日入离职、跨月、存量回流、调岗、流转叠加、来源为平台、来源公司已注销、重跑幂等）全部通过；A 公司的人被释放后入职 B 公司，A 公司每天收 8 元、平台收 2 元

- 编写运维手册和客服常见问题

## 4. 端到端验收清单（上线门槛）

1. 扫码注册 → 私域 → 24h 内无人跟进 → 自动变公域，用户收到通知
2. 自主注册 → 公域匹配全平台 → 报名 B 公司 → 只能看到 B 公司（临时私域）→ 面试未通过 → 回到公域
3. 私域用户 → 匹配度 <80% → 经纪人工单 → 二次推荐不满意 → 释放 → 入职 C 公司 → 流转费按 8 / 2 分账
4. 入职确权 → 电子签 → 在岗 → 次日开始计服务费 → 离职 → 停止计费、合同终止、预支欠款结清
5. 新公司入驻 → 3 个月内导入花名册 → 期满锁定存量基数 → 之后新增人员开始计费
6. 公司注销 → 所有用户批量解绑成公域 → 来自这家公司的流转费改为全归平台
7. 月末生成账单 → 老板端查看 → 提出异议 → 平台复核
8. 每个角色只能看到权限矩阵允许的数据（自动化越权测试）

## 5. 测试策略

| 层 | 内容 | 覆盖要求 |
|---|---|---|
| 单元测试（JUnit 5） | 状态机、派生规则、计费公式、匹配打分 | ≥ 95%，状态迁移表逐条覆盖，包括禁止的迁移 |
| 集成测试 | 每个模块的 Service 连真实 MySQL / Redis（Testcontainers）；ArchUnit 检查模块依赖 | 核心模块全覆盖 |
| 计费黄金用例 | 固定输入 → 固定账单，每次合并都跑 | 100% 通过才能合并 |
| E2E | Playwright：后台用桌面视口，H5 用 iPhone / 低端安卓视口模拟 | 第 4 节 8 条 |
| 定时任务 | 用可控时钟（注入 `Clock`）模拟跨日、跨月、24h 到期 | 每个任务至少覆盖一次重跑 |

## 6. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 阻断项迟迟不裁定 | 状态机和计费返工 | W1 末是硬截止；没裁定的按核验报告的建议口径先做，规则全部做成可配置 |
| 资质或备案没有批下来；H5 域名被微信拦截 | 无法上线 / 扫码打不开 | W1 提交申请；准备 2 个备案域名，提前做微信安全检测 |
| 电子签对接周期长 | M2 延期 | 适配器加 Mock 先开发；准备「线下签 + 上传扫描件」的降级方案 |
| 计费口径出错 | 对企业失信、资损 | 黄金用例；账单在下发前给平台财务复核一次；规则版本化，可以重算 |
| 蓝领用户的手机性能和网络差 | 转化率下降 | 路由懒加载、首屏 JS 不超过 150KB、低端机首屏 2 秒以内、关键接口支持弱网重试 |
| 个人信息合规 | 法律风险 | 加密、脱敏、最小化收集、原图不留存；上线前完成个人信息保护影响评估 |
