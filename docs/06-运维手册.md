# 06 · 运维手册

> 适用版本：V1.0。部署形态：阿里云 ECS（后端 ≥ 2 实例）+ RDS MySQL 8 + Redis + OSS + SLB / Nginx。
> 本手册与 `deploy/` 目录配套：`nginx/`（Nginx 配置）、`Dockerfile.server`（后端镜像）、`scripts/`（备份与恢复演练）。

## 1. 组件与域名

| 组件 | 说明 | 示例域名 / 地址 |
|---|---|---|
| C 端 H5 | `web/apps/seeker/dist` | `m.shitu.com`（含 `/r/{code}` 渠道短链） |
| 驻场 H5 | `web/apps/staff/dist` | `staff.shitu.com` |
| 公司后台 | `web/apps/console/dist` | `admin.shitu.com` |
| 平台中台 | `web/apps/ops/dist` | `ops.shitu.internal`（**仅内网 + IP 白名单**） |
| 后端 | `shitu-server`（Spring Boot，端口 8080），无状态，可水平扩展 | 内网 `10.0.0.11/12:8080` |
| MySQL 8 | 业务库 `shitu`，Flyway 启动时自动迁移 | RDS |
| Redis | 限流、验证码、会话吊销名单（多实例必须） | 云 Redis |

四个前端都通过**同源** `/api/` 访问后端（refresh token 是 HttpOnly + Secure Cookie，跨域无法携带）。

## 2. 环境变量（生产必填）

后端以 `SPRING_PROFILES_ACTIVE=prod` 启动。`ProductionGuard` 会在启动时逐项检查，**任一项不满足直接拒绝启动**并打印原因。

| 变量 | 说明 |
|---|---|
| `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` | 业务库；密码不能为空或 `root` |
| `DB_SSL` | 默认 `true` |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | Redis |
| `SHITU_ENC_KEY` | 字段加密密钥（AES-256，Base64 32 字节）。**丢失 = 全部手机号 / 身份证 / 姓名无法解密** |
| `SHITU_MAC_KEY` | 盲索引密钥（HMAC，Base64 32 字节）。更换会导致按手机号 / 身份证查找全部失效 |
| `SHITU_JWT_SECRET` | 访问令牌签名密钥（Base64 ≥ 32 字节）。更换会让所有人重新登录 |
| `SHITU_COOKIE_SECURE=true` | refresh cookie 只走 HTTPS |
| `SHITU_KV_TYPE=redis` | prod 默认即 redis |
| `SHITU_H5_PUBLIC_BASE` | 渠道二维码前缀，必须 `https://`，如 `https://m.shitu.com` |
| `SHITU_H5_ENTRY` | `/r/{code}` 302 的落地页，默认 `/` |
| `SHITU_STORAGE_DIR` | 上传文件目录（接入 OSS 前），容器内建议 `/data/uploads` 并挂载持久卷 |
| `SHITU_OPS_INIT_PASSWORD` | 首次启动创建超级管理员 `admin` 的初始密码；首次登录强制修改 |
| `SHITU_LOG_DIR` | 日志目录，默认 `/var/log/shitu` |
| `shitu.allow-mock-providers` | **仅预发 / 试点环境**可设为 `true`，允许短信、实名、电子签仍走 Mock |

生成密钥：`openssl rand -base64 32`。三把密钥放 KMS / 密钥管理服务，**与数据库备份分开保管**。

## 3. 发布流程

1. CI 通过（后端单元 + 端到端验收、前端类型检查 + 构建）。
2. 后端：`cd server && mvn -B -Paliyun package -DskipTests` → `docker build -f deploy/Dockerfile.server -t shitu-server:<版本> server/shitu-app/target`。
3. **数据库迁移**：新版本第一个实例启动时由 Flyway 自动执行（迁移脚本只增不改，已执行的脚本禁止修改）。迁移含大表 DDL 时，先在只读低峰期单独启动一个实例完成迁移，再滚动其余实例。
4. 滚动发布：SLB 摘除一台 → 停止（`server.shutdown=graceful`，等进行中的请求完成）→ 启动新版本 → 探活 `GET /actuator/health` 返回 `UP` → 挂回 SLB → 下一台。
5. 前端：`cd web && pnpm install --frozen-lockfile && pnpm build`，把各 `dist/` 同步到 Nginx 根目录。`index.html` 不缓存、`/assets/` 带 hash 长缓存，替换文件即生效。
6. 定时任务由 ShedLock 保证多实例只跑一次，无需特殊处理。

回滚：后端回到上一个镜像即可（迁移脚本都是向后兼容的增量变更）；前端回滚 `dist/`。

## 4. 定时任务

| 任务 | 时间 | 作用 | 漏跑的影响 / 处理 |
|---|---|---|---|
| `outbox_dispatch` | 每 2 秒 | 投递发件箱事件（通知、释放等副作用），失败指数退避，满次数进死信 | 通知延迟；看 `shitu_outbox_pending` / `shitu_outbox_dead` |
| `response_window_scan` | 每分钟 | 24h 响应窗口超时 → 私域转公域 / 报名释放 | 用户被错误占住；看 `shitu_response_window_overdue` |
| `follow_up_reminder` | 每分钟 | 窗口剩 4h / 1h 提醒驻场 | 只影响提醒 |
| `broker_sla` | 每分钟 | 经纪人 2h 联系 / 24h 处理时限，超时自动释放 | 工单不释放 |
| `job_weight` | 每小时 05 分 | 岗位真实权重重算 | 排序不更新，次小时自愈 |
| `daily_billing` | 每天 00:30 | 前一天的服务费与流转费（幂等，可重跑） | 中台「计费 → 重跑某日」补算 |
| `job_health` | 每天 01:30 | 陈旧岗位暂停与扣分、诚信分复核 | 次日自愈 |
| `monthly_bill` | 每月 1 日 06:00 | 生成上月账单并下发 | 中台「生成月度账单」手动触发 |

## 5. 监控与告警

指标：`/actuator/prometheus`（Nginx 已对外屏蔽 `/actuator/`，只在内网抓取）。

| 告警 | 规则 | 处理 |
|---|---|---|
| 实例不可用 | `up == 0` 或健康检查失败 1 分钟 | 看日志；SLB 已自动摘除 |
| 5xx 比例 | `http_server_requests_seconds_count{status=~"5.."}` 5 分钟占比 > 1% | 按 traceId（响应头 / 响应体 `traceId`）查日志 |
| 接口慢 | P95 > 1s 持续 5 分钟 | 查慢 SQL、连接池 `hikaricp_connections_pending` |
| 连接池耗尽 | `hikaricp_connections_pending > 0` 持续 1 分钟 | 扩实例或调大 `DB_POOL_SIZE`（注意 RDS 最大连接数） |
| 发件箱积压 | `shitu_outbox_pending > 500` 持续 5 分钟 | 投递任务卡住或下游（短信）故障，见 §7 |
| 发件箱死信 | `shitu_outbox_dead > 0` | 看 `outbox_event.last_error`，修复后把状态改回 `PENDING` 重放 |
| 24h 窗口超时未处理 | `shitu_response_window_overdue > 0` 持续 5 分钟 | `response_window_scan` 没跑：查 `shedlock` 表锁是否被异常持有 |
| 计费漏跑 | `shitu_daily_billing_lag_days > 1`（上午 9 点检查） | 中台重跑缺失日期 |
| JVM 内存 | 老年代使用 > 85% 持续 10 分钟 | 导出堆栈后重启该实例 |

日志：`/var/log/shitu/shitu-server.log`，按 200MB 滚动保留 30 天；每条请求带 `traceId`。日志里不打印手机号、身份证、验证码明文。

## 6. 备份与恢复

- **RDS 自动备份**：每日全量 + binlog 保留 7 天（支持按时间点恢复）。
- **额外副本**：`deploy/scripts/backup-mysql.sh` 每天 02:30 导出一份到异地存储，保留 14 天。
- **恢复演练**：每月一次运行 `deploy/scripts/restore-drill.sh`（恢复到临时库、核对关键表行数与 Flyway 版本后删除），结果记录到运维台账。
- 备份中的敏感字段是密文。**恢复后必须使用同一套 `SHITU_ENC_KEY` / `SHITU_MAC_KEY`**，否则数据不可读。
- 上传文件（营业执照、合同）：接入 OSS 后开启版本控制与跨区域复制；本地目录阶段对 `SHITU_STORAGE_DIR` 每日打包备份。

## 7. 常见故障处理

| 现象 | 排查 | 处理 |
|---|---|---|
| 用户收不到验证码 | 短信平台控制台发送记录；日志 `sms` | 通道故障时切备用通道；图形验证码频繁弹出 = 同 IP 发送过多（`shitu.sms.captcha-after-per-ip`） |
| 签约后一直「待签署」 | e签宝回调日志（`/api/v1/callback/esign`）；签名校验失败会记 WARN | 回调可重复推送（幂等）；必要时在 e签宝控制台重推 |
| 计费金额异常 | 中台「账单明细」逐日核对 `billing_daily` | 修正数据后「重跑某日」；已下发账单走异议流程 |
| 公司被误封禁 | 审计日志 `COMPANY_PENALIZED` / `COMPANY_STATUS_CHANGE` | 超管在中台恢复状态（会清除状态缓存） |
| 用户说身份证被占用 | 中台「实名复核」查看申诉；原账号在岗时不能直接解除 | 按 D-45 处理 |
| 某接口大量 401 | 时间不同步会导致令牌提前过期 | 校时（chrony），所有实例 NTP 同步 |

## 8. 安全基线

- 平台中台只在内网域名开放，Nginx IP 白名单；超管账号开启强密码并定期轮换。
- 服务器只开放 443（Nginx）与内网端口；数据库、Redis 不暴露公网。
- `X-Forwarded-For` 由 Nginx 覆盖写入真实 IP，后端只信任内网代理（限流与审计依赖真实 IP）。
- 第三方回调（e签宝）只接受签名正确的请求。
- 每季度做一次越权与注入复测（`RoleMatrixIT` 覆盖的角色矩阵 + 人工渗透）。

## 附：预览环境（单机、无域名）

还没有域名、证书和第三方通道时，用 `deploy/preview/` 在一台 Ubuntu 机器上起一个给内部看效果的环境。它**不是**生产环境：

- 后端以 `SPRING_PROFILES_ACTIVE=preview` 启动（`application-preview.yml`）：走 HTTP、短信 / 实名 / 电子签是模拟实现、**短信验证码直接回显在页面上**、带演示公司。任何人都能用任意手机号登录，所以只能放演示数据。
- `PreviewGuard` 启动检查：三把密钥不能是仓库里的开发默认值，数据库密码和平台初始密码必须设置。
- 四个前端共用一个端口 8888，按路径区分：`/` 求职端、`/staff/` 驻场端、`/admin/` 公司后台、`/ops/` 运营中台。构建时要带路径：`npx vite build --base=/staff/`（求职端用默认的 `/`）。
- MySQL、Redis、后端都只监听 127.0.0.1，对外只有 Nginx 的 8888。

安装：把 `shitu-server.jar`、四个前端的 `dist` 打成 `seeker.tgz / staff.tgz / console.tgz / ops.tgz`、`shitu-preview.nginx.conf`、`setup.sh` 传到服务器 `/opt/shitu/upload/`，执行 `PUBLIC_BASE=http://<公网IP>:8888 bash setup.sh`。脚本可重复执行（更新版本时重传文件再跑一遍），已生成的密钥不会被覆盖。

- 密钥与密码：`/etc/shitu/shitu.env`（仅 root 可读）。平台管理员 `admin` 的初始密码是其中的 `SHITU_OPS_INIT_PASSWORD`，首次登录强制修改。
- 日志：`/var/log/shitu/shitu-server.log`；服务：`systemctl status shitu`。
- 转正式环境时不要沿用这台机器的数据：换 `prod` profile、域名 + HTTPS、真实通道，按本手册第 2 节重新部署。
