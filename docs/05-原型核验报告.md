# 05 · 原型核验报告

> 核验对象：`prototype/` 全部 6 个页面（index / app / staff / admin / platform / spec）
> 核验依据：《V1.0 MVP 完整产品文档 V2.0》《版本规划·最终定稿》（均 2026-07-23）
> 核验方式：逐页抽取文本，对照文档章节；交叉比对原型各页之间、原型与 `spec.html` 之间的口径。

## 结论

原型整体质量高：文档第 1–15 章的功能点全部有对应页面；`spec.html` 补齐了数据字典、状态机、定时任务、事件、边界约定，足以直接指导后端开发；`index.html` 自带的「开发前待确认清单」已识别出 3 条阻断问题，判断准确。

本次核验**新发现 9 处问题**：2 处原型内部互相矛盾，3 处规则缺口会直接影响后端实现，2 处范围超出 V1.0 边界但未标注，2 处统计数字过期。下表中「新」指原型自带待确认清单里没有的。

## A. 原型内部互相矛盾（必须修正原型）

### A-1【高·新】薪酬预支审批级数：三处页面三种说法

| 位置 | 写法 |
|---|---|
| `admin.html` A-17 薪酬预支审批页 | 「员工本人发起 → 驻场初审 → 项目经理终审 → 拨款（**双级审核**）」 |
| `admin.html` 组织与权限 A-19 权限矩阵 | 预支审批：驻场「初审」/ 项目经理「**复审**」/ 老板「**终审**」（**三级**） |
| `admin.html` 老板数据总览 A-14 | 「4 笔薪酬预支**待终审** 合计 ¥2,000」（老板终审） |
| `admin.html` 薪资权限说明（约第 878 行） | 「预支审批**不含老板**」 |
| 左侧菜单 | A-17 挂在「劳务公司老板」分组下 |
| `staff.html` M-11 | 双级（驻场 → 项目经理终审） |

`index.html` 写的是「已按最终定稿实现双级」，但 A-14、A-19 和菜单位置都没跟着改。
**建议**：按《版本规划》2.1-6 定为双级。A-19 矩阵里老板一栏改为「✕（可查看汇总）」，项目经理改为「终审」；A-14 那条待办删除；A-17 移到「项目经理」菜单分组。

### A-2【中·新】`spec.html` 的枚举和状态迁移表对不上

- 枚举 `user_status` 定义了 `RESIGNED 已离职` 和 `UNFOLLOWED 未被跟进`，但迁移表里**没有任何一条迁移的目标是 `UNFOLLOWED`**，所有释放路径都指向 `PUBLIC_SEEKING`。
- 迁移表写 `EMPLOYED → RESIGNED`，而文档 3.4 状态表写的是「A 公司二维码注册 → 离职 → **公域求职**」。如果 `RESIGNED` 是一个独立状态，就缺一条 `RESIGNED → PUBLIC_SEEKING`，否则离职用户卡在这个状态里不能匹配。

**建议**：`user_status` 只保留 6 个运行态（GUEST / PUBLIC_SEEKING / PRIVATE_PENDING / PENDING_INTERVIEW / PENDING_CONFIRM / EMPLOYED）。离职和超时都迁移到 `PUBLIC_SEEKING`，另记 `last_release_reason`（RESIGNED / TIMEOUT_24H / …）。C 端「我的工作 · 已离职」这类展示由「状态 + 原因」推出来。这样每种状态的匹配范围只有一种算法。

## B. 规则缺口（影响后端实现，需产品裁定）

### B-1【高·新】「我的报备 · 待确认」：第三方报备是一条文档里没有的入口

`app.html` S-25 的「待确认」卡片：**宏泰人力**的「引流人（脱敏）」替用户发起了一条蓝思科技岗位的报备，用户可以「同意 / 拒绝」，超时自动作废。原型的意思是：别的劳务公司可以把岗位直接推到用户面前。

这条入口和核心规则冲突：
- R-01「匹配是唯一入口、无任何报名通道」：报备等于绕过 AI 问薪的报名通道；
- 公私域保护：如果用户当前是鑫诚的私域，宏泰能不能对他发起报备？如果能，24h 保护窗口就形同虚设；
- 归属：用户同意之后，`bound_company_id` 写宏泰吗？流转费怎么算？

文档 6.3 只给了标签名「待确认」和「脱敏引流人操作权限：待确认可同意/拒绝」，**没有定义谁发起、发起条件是什么、同意后状态怎么迁移**。
**建议**：V1.0 先砍掉「待确认」入口，只保留经纪人二次匹配这一条人工推荐路径（T-203：经纪人推荐 → 用户在 C 端确认 → 走正常实名报名）。如果产品坚持要保留，就必须补一张「报备」状态迁移表，并且规定**只能对公域用户发起**。

### B-2【高·新】增长技术服务费：「按人数差算」和「按人打存量标记算」结果不同

- 文档 2.2 / `spec` 07 的公式：`增量 = 当前在岗人数 − 存量基数`（按人数差算）
- `spec` 01 `billing_daily` 表：每人一行，带 `is_stock` 字段，「true 则不计费」（按人打标记）

**举例**：存量基数 180 人，之后存量员工走了 50 人，又新招 70 人，当前在岗 200 人。
- 按人数差算：增量 = 200 − 180 = **20 人**计费
- 按人打标记算：存量标记的只剩 130 人，新招的 **70 人**全部计费

文档里「存量人员永久免费，不受离职影响」两种都解释得通。**每天的计费金额差 3.5 倍，必须裁定。**
**建议**：按文档公式，在公司层面用人数差算钱（对企业友好，和「引导全量导入」的设计目的一致）；`billing_daily` 按人记明细只用于审计，不作为计费依据。E-06「存量人员回流」在这个口径下自然成立。

### B-3【中·新】岗位权重：「时间衰减」和「低转化降权」叠在一起会重复惩罚

文档 12.2（按转化表现降权）和 12.3.2（按挂岗天数衰减）是两套规则。P-13 匹配引擎把两者**相乘**：
`岗位权重 = 挂岗衰减 × 低转化系数 × 诚信系数 × 限流系数 × 名额系数`

结果：
- 一个挂了 35 天、入职一直很好的岗位，只因为时间就降到 20%，和 12.2「低转化的岗位才降权」的初衷相反；
- 一个挂了 20 天、转化率低于 10% 的岗位，得到 50% × 0.5 = **25%**，比 12.2 规定的 50% 罚得更重。

**建议**：两者取较小值，不相乘。另外，有入职转化的岗位不参与时间衰减，或者每次有新入职就把衰减重置一次。

### B-4【中·新】预支「每月最多 4 次」实际几乎用不满

规则：每满 7 个在岗日 +1 次机会，月末清零不结转。要在一个自然月里拿到第 4 次，需要 **28 个在岗日**。S-48 的示例数据就是在岗 18 天只解锁 2 次。所以「月上限 4 次」实际上是个摆设。文档另有「入职满 7 天才能首次预支」，原型没说明这个 7 天和每月的 7 天计数是什么关系。
**需裁定**：在岗日计数是按月重新开始，还是滚动累计？入职第 7 天是否同时解锁第 1 次机会？

### B-5【低·新】「重新匹配几次触发流转」：文档和 spec 不一致

文档写「重新匹配 **2–3 次**后仍不满意」，`spec` 写「`match_count` ≥ **3** 次触发流转建议」。并且 `match_count` 是累计计数，被释放之后要不要清零也没写。
**建议**：做成平台可配的参数，默认 3 次；以「一个求职周期」（两次报名或释放之间）为单位计数。

## C. 范围超出 V1.0 边界，但没标出来

### C-1【高·新】在岗打卡（S-47 / S-48 / M-13 / M-14）

《版本规划》2.2 明确写了「V1.0 不包含：打卡考勤体系」，而且 LBS 打卡在 3.2.2 被列为 V1.5 核心模块。原型却在 V1.0 里加了 4 屏打卡，并在 S-47 里写「**打卡是唯一的在岗日认定方式**」，这等于改了预支准入规则（文档的口径是「入职满 7 天」）。`index.html` 的「V1.0 交付边界 · 原型中已按此标记的模块」表里**没有列出这 4 屏**。

这个设计思路本身有价值：用工人自己打卡来认定在岗日，平台就有了一个不依赖劳务公司的数据来源。但它会带来 LBS 围栏、补卡流程、驻场核对、补录比例风控等一整套工作量，约增加 1.5–2 周。
**建议**：V1.0 的在岗日按「入职确权日起算的自然日，扣除驻场标记的请假和缺勤」计算。打卡整体放到 V1.5 和考勤一起做。原型里给这 4 屏加上 V1.5 标记。

### C-2【中】工资发放模块（S-41~43、A-08、A-09）

原型标的是「规划外 · 建议 V1.5」，这一点没问题。但文档节点八「离职时从工资中扣除预支欠款」、6.5「次月发薪日系统自动抵扣」在 V1.0 就要用到工资数据。
**建议**：V1.0 只做「工资表 Excel 导入 + 预支抵扣计算 + C 端工资条查看」，不做核算和代发审批流（已决策，见 04-决策记录 D-28）。
